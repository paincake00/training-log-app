# AGENTS.md — правила работы над проектом

Этот файл обязателен для любого агента, который меняет код в репозитории.

## 1. Источник истины

- `PLAN.md` — что строим, модель данных, поведение, acceptance criteria.
- `DESIGN.md` — UI-стандарт, компоновка, типографика, состояния.
- `AGENTS.md` — процесс работы, качество, тесты.

Перед изменениями прочитай все три. Если требование противоречит коду или другому документу — остановись и спроси пользователя, не выбирай «по вкусу».

Не расширяй scope. Всё, чего нет в MVP `PLAN.md`, — только после явного согласования.

Если решение по продукту изменилось, обнови `PLAN.md`/`DESIGN.md` в том же изменении.

---

## 2. Декомпозиция и суб-агенты (обязательно)

Контекст и токены — ограниченный ресурс. Ведущий агент не должен тащить в один контекст всю реализацию, весь код и всю отладку.

Правила:

- Любую нетривиальную задачу (фича, рефакторинг, миграция, разбор бага) ведущий агент сначала **декомпозирует**.
- Для задач, затрагивающих больше одного слоя (data + UI + тесты), используй **минимум двух суб-агентов**:
  1. `explore` — разведка кода, поиск файлов и зависимостей, если контекст неизвестен;
  2. `coder` — реализация изолированной части;
  3. `reviewer` — независимая проверка после интеграции.
- Если части независимы и не редактируют одни файлы — запускай их параллельно. Если пересекаются — только последовательно.
- Не позволяй двум суб-агентам одновременно менять одни и те же файлы.
- Промпт суб-агенту должен быть самодостаточным: цель, файлы, ограничения из `PLAN.md`/`DESIGN.md`, критерии приёмки, команды тестов.
- После каждого суб-агента ведущий агент:
  - смотрит diff;
  - запускает тесты;
  - проверяет, что не сломаны соседние сценарии;
  - только потом идёт дальше.
- Простую правку в одном файле можно сделать напрямую, без суб-агентов.
- Не заставляй `reviewer` править код: он только читает и отчитывается.

Цель — маленький чистый контекст у ведущего агента: план, diff, результаты тестов, а не вся переписка по реализации.

## 3. Тесты и проверка (блокирующее требование)

**Ни одна фича не считается готовой без тестов на данные и логику.**

Обязательно:

- Каждый метод repository/DAO, каждая транзакция, копирование плана в тренировку, reload, уникальность, порядок, удаление, каскады и краевые случаи — покрыты тестами.
- Чистая логика — JUnit.
- Room и repository — Robolectric с in-memory БД (или instrumented, если окружение позволяет).
- UI-тесты — там, где они дают реальную пользу (критичные потоки, вёрстка длинного текста). Не заменяют тесты данных.
- Багфикс: сначала воспроизводящий тест (когда это возможно), потом исправление.
- Запрещено отключать, удалять или «подгонять» падающие тесты без объяснения и согласования.
- Запрещено оставлять `@Ignore` без причины и тикета/пометки в `PLAN.md`.

Минимальная проверка перед отчётом:

```bash
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
export ANDROID_HOME="$HOME/Library/Android/sdk"
./gradlew testDebugUnitTest
./gradlew assembleDebug
```

Обе команды должны пройти. В отчёте укажи, что именно запускал и результат.

Дополнительно перед завершением задачи:

- пройди acceptance criteria из `PLAN.md`;
- проверь, что изменение не сломало соседние фичи;
- проверь, что нет `INTERNET` в манифесте и приложение работает офлайн;
- при UI-изменениях пройди чек-лист из `DESIGN.md`.

## 4. Работа с данными

- Все изменения, затрагивающие несколько таблиц, — в `@Transaction`.
- Схема Room версионируется. После появления реальных данных любые изменения схемы — только через миграции. Destructive fallback запрещён.
- `exportSchema = true`; схемы хранятся в `app/schemas`.
- Не удаляй пользовательские данные неявно. Удаление — только по явному действию с подтверждением.
- Соблюдай разделение из `PLAN.md`:
  - название/описание — глобальные;
  - `lastProgress` — последняя известная прогрессия пресета;
  - прогрессия плана — своя у каждого дня;
  - фактическая прогрессия — своя у каждой тренировки.
- Не «упрощай» это разделение без согласования.
- Даты: `LocalDate` → `epochDay`; день недели — ISO 1..7.
- Позиции после удаления/перестановки — без дыр.
- Уникальные индексы из `PLAN.md` обязательны.

## 5. Код

- Kotlin, Jetpack Compose, Material 3, MVVM + Repository.
- Одна Activity, без Hilt; DI вручную через `AppContainer`.
- Бизнес-логика — вне Composables. Composables только отображают состояние и отправляют события.
- Состояние — `StateFlow`/`Flow`; не блокируй main thread.
- Не добавляй зависимости без необходимости. Любая сетевая библиотека запрещена.
- Следуй стилю окружающего кода; не переформатируй чужие файлы без причины.
- Не оставляй мёртвый код, закомментированные блоки и `TODO` без пометки.
- Все пользовательские строки — в `strings.xml`, русский.
- Никаких хардкод-строк в Compose.
- Даты и числа — через локаль `ru`.
- Прогрессия хранится и отображается как есть, без парсинга и автоформатирования.

## 6. UI

- Следуй `DESIGN.md`.
- Учитывай `statusBars`, `navigationBars`, IME, edge-to-edge.
- Никаких фиксированных высот у текстовых контейнеров.
- Проверяй длинные названия, описания и прогрессию, тёмную/светлую тему, крупный системный шрифт.
- Destructive-действия — через меню и подтверждение.
- Все интерактивные элементы — минимум 48dp, с `contentDescription`.
- После UI-правок проверь, что ничего не наползает и не обрезается.

## 7. Рабочий процесс

1. Прочитай `PLAN.md`, `DESIGN.md`, этот файл.
2. Составь короткий todo-план.
3. Разведай код (`explore`), если контекст незнаком.
4. Сформулируй тесты/критерии приёмки.
5. Декомпозируй и реализуй (суб-агенты, если задача нетривиальная).
6. Прогони тесты и сборку.
7. Сделай независимый review (`reviewer`) для нетривиальных изменений.
8. Проверь acceptance criteria и отсутствие регрессий.
9. Отчитайся: что изменено, какие тесты запущены, что осталось.

Не отчитывайся «готово», если тесты или сборка красные.

---

## 8. Definition of Done

- [ ] Поведение соответствует `PLAN.md`.
- [ ] UI соответствует `DESIGN.md`.
- [ ] Данные и логика покрыты тестами.
- [ ] `testDebugUnitTest` — зелёный.
- [ ] `assembleDebug` — зелёный.
- [ ] Нет регрессий в существующих тестах.
- [ ] Acceptance criteria проверены.
- [ ] Нет сетевых разрешений/библиотек.
- [ ] Документация обновлена, если поведение изменилось.

## 9. Инструменты и окружение

### Context7 MCP — обязателен для API

Перед работой с Compose, Room и Gradle не полагайся на память — проверяй актуальные сигнатуры и версии через Context7:

- Jetpack Compose: `/websites/developer_android_reference_kotlin_androidx_compose`
- Room: `/websites/developer_android_training_data-storage_room`
- Android Gradle Plugin: `/websites/developer_android_build`

Дополнительные MCP-серверы (`api-anything`, `opencode`) и `report` для этого проекта не нужны. `google_search` допустим только для проверки совместимости версий и release notes, не как замена документации API.

### Скиллы

Глобально установлен `find-skills`. Для проекта локально установлены официальные Android-скиллы:

- `.agents/skills/testing-setup` — стратегия тестирования, настройка unit/UI/screenshot/e2e-тестов;
- `.agents/skills/edge-to-edge` — edge-to-edge, системные бары и IME-инсеты.

Используй их по необходимости. Правила проекта всё равно имеют приоритет: `PLAN.md`/`DESIGN.md` — источник истины.

Если `npx skills add` падает с ошибкой авторизации GitHub, причина в глобальном git-конфиге, который переписывает HTTPS на SSH. Обход для установки:

```bash
GIT_CONFIG_GLOBAL=/dev/null npx -y skills add <package> --skill <skill> -y
```

### Устройство для проверки UI

К проекту подключён физический телефон:

- модель: Pixel 9a (`tegu`);
- серийный номер: `59111XEBF5F391`;
- Android 17, API 37;
- состояние adb: `device` (отладка по USB разрешена).

Проверка:

```bash
"$HOME/Library/Android/sdk/platform-tools/adb" devices -l
```

Устройство — основной таргет для ручной проверки UI и Compose UI-тестов. AVD не создан и для базовой разработки не обязателен. `compileSdk`/`targetSdk` проекта — 36, телефон работает на API 37: приложение должно запускаться, но поведение на новой версии Android нужно проверять на устройстве.
